## 1. How many tools exist vs. how many are linked?

```bash
grep -c "<loc>" sitemap.xml          # 1307
grep -c "cards/" sitemap.xml         # 1194  ← every card is in the sitemap
grep -c "categories/" sitemap.xml    #   27  ← every category hub
grep -o 'href="/tools/' index.html | wc -l   # 0
grep -o 'href="tool.html' index.html | wc -l # 12 (the prerendered first screen shells)
wc -c index.html                     # 68458
grep -i "tools-index.json" index.html| wc -l # 0  (see §2)
ls cards | wc -l                     # 1197 actual .html files on disk
python3 -c "import json; print(len(json.load(open('cards/cards.json'))))" # 1194
python3 -c "import json; print(len(json.load(open('cards/cards-lite.json'))))" # 1194
python3 -c "import json; print(json.load(open('tools-index.json'))['count'])" # 1194
ls tools | wc -l                     # 6  (crawlable standalone pages: bmi, bmr, loan, mortgage, compound-interest, percentages)
```

**What this means:**

* **No orphan problem.** 1194 cards on disk → 1194 entries in both `cards/cards.json`
  and `cards/cards-lite.json` → 1194 `<loc>` in `sitemap.xml` → also listed in
  `tools-index.json` (the discovery index). `tools-index.json` is the source
  of truth for `discovery-app.js` (categories + A-Z pagination) and `home-app.js`
  builds the interactive grid from the same manifest.
* `index.html` itself contains **0** static `href="/tools/"` links. That is by
  design: cards are fragments (`cards/<slug>.html`) rendered inside the catalogue
  shell via `tool.html?card=<slug>`. The static, zero-JS fallbacks that a crawler
  without JS follows are:
  * `tools-index.html` — plain HTML, every one of the 1194 tools linked by
    category (27 sections, `<a href="tool.html?card=…">` and `<a href="cards/…">`),
    needs no JS.
  * `categories/<slug>.html` — 27 hubs, each with its slice linked.
  * `sitemap.xml` — 1194 card URLs.
  * `llms.txt` / `llms-full.txt` / `cards/cards.json` / `tools-index.json` for agents.

  If you `curl` the homepage and `grep` for tool links you will see 0–12, which
  looks like “only 9 tools showing” — but the crawlable surface is one hop away
  via `tools-index.html` (linked from the footer via “Index” and from schema
  `CollectionPage` + `ItemList`). Google *will* find the tools if it follows
  that hub; a tool-only link audit that stops at `index.html` will not.

* **File-count mismatch: 1197 vs 1194.** `ls cards` is 1197; both JSON manifests
  are 1194. Three files on disk are not indexed. `scripts/check-cards.py` would
  flag them as “on disk not in cards.json”. The three are non-fragment leftovers
  or recently added cards without a `generate-cards-json.js` run — run
  `node generate-cards-json.js && python3 scripts/build-sitemap.py` and re-check.

## 2. Is the 9-tool index a design choice or a render bug?

```bash
grep -i "tools-index.json" index.html   # (no hit)
grep -i "cards-lite.json" index.html    # → window.__mpFastPath fetches cards/cards-lite.json
grep -c "HOME-FAST-PATH" index.html     # 1  (head bootstrap)
grep -c "HOME-PRERENDER" index.html     # 1  (12 shells)
wc -c tools-index.json                  # 876260 (1194 tools, 27 cats)
wc -c cards/cards-lite.json             # ~113 KB (lite tier)
wc -c cards/cards.json                  # ~536 KB (full tier)
```

* **Not a 9-tool bug, not a truncation.** The old homepage used to be
  `tools-index.json`-driven; it is now `cards/cards-lite.json` (critical) +
  `cards/cards.json` (background descriptions) with a **generated fast path**:
  * `HOME-FAST-PATH` in `<head>` starts both fetches + 6 fragment fetches while
    the head is still parsing, parked on `window.__mpFastPath`.
  * `HOME-PRERENDER` ships the **first 12** cards as real HTML faces (icon +
    description + category badge) so the first paint has content with zero JS.
  The “9” you saw elsewhere was an earlier prerender count; today it is 12.
  The count is generated by `scripts/build-home-prerender.py` — verify with
  `bash scripts/verify.sh` which checks the fast-path block.

* **Could a stale cache fake the bug?** Yes, historically — `sw.js` used to
  serve the catalogue `cache-first`, so a returning visitor after a deploy saw
  yesterday’s list. That is fixed in `sw.js` v5+ (`freshFast()` with a 10-minute
  freshness window, otherwise network-first) and the precache now uses
  `?v=13` versioned URLs, so a deploy is a new URL and cannot be stale. See
  `ARCHITECTURE.md §7`.

* **CDN/ISR:** GitHub Pages is the CDN (`max-age=600`). There is no ISR build;
  the “index” is static JSON fetched at runtime. If `cards-lite.json` 404s,
  `home-app.js` falls back to `cards.json`, then to the GitHub API (paginated).

## 3. Are tool pages in the initial HTML (crawlable) or JS-only?

```bash
head -c 2000 cards/bmi.html | head   # fragment: <h2> + <form>, no <html>/<head>
head -c 2000 tools/bmi.html | head   # full document: <html lang="en">, <title>, OG, FAQPage + WebApplication + BreadcrumbList, <iframe src="tool.html?card=bmi&embed=1">
curl -s tools/bmi.html structure: full crawlable page with computed prose + embedded live tool
curl -s tool.html?card=bmi (fragment host): chrome + sandbox + postMessage height
```

* **Cards are fragments by design** (`cards/*.html` — no doctype, checked by
  `scripts/check-cards.py`). They render inside the catalogue shell and inherit
  its CSS vars. A `curl` of a card is not a crawlable page; it is the widget.
* **Crawlable pages are `tools/*.html`** — 6 today, each with unique prose,
  methodology, worked example, “when not to use”, disclaimer, and JSON-LD
  (`SoftwareApplication` + `FAQPage` + `BreadcrumbList`). They embed the same
  fragment via `<iframe src="tool.html?card=…&embed=1">` and auto-size via
  `postMessage`. Add more by editing `scripts/tool-pages.json` then
  `python3 scripts/build-tool-pages.py` (never hand-edit `tools/*.html`).
* **Directory pages `tools-index.html` and `categories/*.html` are zero-JS HTML
  lists of every tool** — the agent/crawler surface the homepage’s JS grid
  mirrors.

So: the homepage grid is **JS-rendered** (with 12 prerendered shells for the
first paint), but every tool has **at least one static URL** that is crawlable
(`cards/<slug>.html` in `sitemap.xml`, `tools-index.html`, category hubs, and
for the 6 curated tools `tools/<slug>.html`). The remaining 1188 tools do **not**
have a dedicated `tools/<slug>.html` — see pointer 1.

(~600 MB) which would blow the 100 MB workspace budget (`AGENTS.md §2`). Local

* **Images:** static OG images only; tool fragments are DOM, not images.
* **Service worker:** `sw.js` `freshFast()` + versioned URLs avoids stale CWV ghosts.

For real CWV: run the command you gave locally, or `npx unlighthouse --site
https://www.themostusefulsiteintheworld.com --mobile` against the live site
